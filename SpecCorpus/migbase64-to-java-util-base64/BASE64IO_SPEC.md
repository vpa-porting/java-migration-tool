# Base64IO 2.2: operational encoding specification

Status: audited semantic loop contract, an executable model, and an active LibSL migration
pair (`specs/base64io-source.lsl` and `specs/base64io-jdk.lsl`). The source specification
abstracts iteration as `FOLD_BASE64_WINDOWS`; the target realizes it using an inline JDK
binding. Neither `readAllBytes()` nor `Base64.Encoder.wrap()` preserves the full stream
protocol specified here. The loop action contract is assumed by the SMT solver; the
binding body is validated empirically, not proved by loop induction.

Source: `com.brsanthu:migbase64:2.2`, `com/migcomponents/migbase64/Base64IO.java`.
Source jar SHA-256: `a849496e3e3472920a6f9f52e80ff864eeb29cdaa98cc0ae37260e23985a7c90`.
The audited source jar and extracted file are retained in `build/source-audit/`.

## API and observations

```text
public static void encode(InputStream in, OutputStream out, boolean lineSep)
    throws IOException
```

Compare final output bytes, the ordered stream-call trace, consumed input, exception class
and identity of injected I/O exceptions. Bulk/single-byte overload dispatch, read offsets
and lengths, output write lengths (including zero) and reuse of scratch arrays are part
of the trace. Flush/close calls are observable: the encoder performs neither, on success
or failure. It never calls available(), mark() or reset(). Constructor smoke checks are
reported separately from encoding comparisons.

Exception messages/stack traces, timing, allocation counts, memory exhaustion and custom
streams inspecting/mutating scratch contents outside the requested ranges are outside the
observation model. Scratch-array identity is included, but external aliasing of its contents
after a call returns is not. Default charset is stable for the life of a JVM; reflective
mutation of private tables/charset caches and custom hostile charset providers are excluded.

The machine accepts ordinary blocking reads that return -1 or a valid count. A finite
sequence of zero returns is additionally tested as robustness behavior: it makes no progress
and triggers another read. Infinite input, endlessly returning zero, or non-returning stream
operations have no termination guarantee and are not generated by the fuzz tests.

## Value alphabet and numeric domain

The 64-symbol standard Base64 alphabet is converted with **String.getBytes() using the
default charset**, not an explicit ASCII charset. Let C be that byte array. A six-bit value
v produces C[v]. With an ASCII-compatible default this is ordinary Base64. With e.g. a
UTF-16 default it is not: indexing happens over encoded bytes, not characters. Padding
is always the literal byte 61 (`=`); CR/LF are always bytes 13 and 10.

The model uses the JDK basic encoder to derive sextets for complete groups/tails, then
translates alphabet positions through C. It does not call MiGBase64 for expected values.
The deterministic whole-input oracle separately uses JDK basic/MIME encoding and the
documented tail rule below. All offsets are bounded by the fixed window and 78-byte packet;
there is no unbounded int32 line counter. Payload bytes are interpreted unsigned.

## State machine

Persistent state:

* `window`: one reused 98,304-byte array (32 KiB × 3);
* `packet`: one reused 78-byte array;
* `cc`: count of full three-byte groups since the last 19-group flush, initially 0;
* `pendingCRLF`: initially false, retained across input windows;
* `filled`: number of input bytes in the current window, initially 0.

### FILL

Execute exactly `in.read(window, filled, 98304-filled)`.

* Return -1: enter EOF-ENCODE with the bytes already accumulated.
* Return a count: add it to filled. If filled is below 98,304, read again without
  emitting any bytes. If full, enter FULL-ENCODE immediately; do not probe for EOF yet.
* Throw: terminate with the same exception. Bytes read into the current partial window
  have not been encoded or written. Prior complete-window output remains committed.

No eager null checks precede this operation. Null input fails here. If both arguments
are null, input failure wins. Input's own bulk-read implementation remains authoritative:
the default InputStream bulk method can catch an IOException after initial progress and
return a short count; the encoder must react to that returned count normally.

### FULL/EOF-ENCODE

At EOF let `tail = filled mod 3` and `aligned = filled-tail`; for a full window,
tail=0 and aligned=98,304. Start a local `queued=0`. For each complete input triple:

1. If pendingCRLF is true, append bytes 13,10 to packet and clear the flag.
2. Append its four translated Base64 alphabet bytes to packet.
3. Increment cc. If cc reaches 19, execute `out.write(packet,0,queued)`, set queued=0
   and cc=0, and set pendingCRLF=true iff lineSep is true.

Then **always** execute `out.write(packet,0,queued)`, even when queued==0. This is
observable for empty input, exact 19-group boundaries, and the EOF pass after a full window.
cc is retained across windows even though each window drains its partial packet. Therefore
one logical 76-character line can span two output calls from different input windows.

For tail=1 or tail=2, append exactly four encoded/padded bytes via a separate
`out.write(packet,0,4)`. This path **does not honor pendingCRLF**. It also does not increment
cc. At EOF return; otherwise reset filled=0 and enter FILL for the next window.

All effects execute before the corresponding state update. A failing write propagates
the same exception immediately; no later read, flush or close occurs. A write can commit
any permitted output prefix before throwing, including part of CRLF or padding.

## Consequences that a target must preserve

* Without line separators, successful output is basic padded Base64 (subject to C's charset).
* With line separators, complete groups are separated into 19-group (76-character) lines;
  CRLF is deferred until another complete three-byte group is available. There is no
  trailing CRLF.
* If n mod 3 is nonzero, floor(n/3)>0 and floor(n/3) mod 19==0, the final padded quartet
  follows the previous line **without CRLF**. At n=58 or 59 the source emits 80 characters
  on one line, while standard MIME Base64 inserts a CRLF. The model preserves source
  behavior; it does not silently repair this discrepancy with the Javadoc/RFC description.
* Empty input still causes one zero-length output write. A null output therefore throws
  NullPointerException even for empty input, after reading EOF. A custom output may throw
  on that zero-length call. Reading may fail before the output is inspected.
* The method buffers up to 98,304 input bytes before emitting anything. An input error at
  byte 75 of a short stream leaves no output, rather than the encoded prefix of those bytes.
* An exact full input window is followed by a separate EOF read and zero-length write.
* The public no-argument Base64IO constructor is callable and creates distinct instances;
  this one-line API path has a separate explicit construction test, not reflection.

## Invariants and migration obligations

For a future source/target pair:

1. FILL maintains 0<=filled<=98304 and preserves all committed prior-window output.
2. cc is always 0..18 and counts full groups globally modulo 19. It must not reset at
   a window boundary; the window contains 32,768 groups, which is not divisible by 19.
3. During group emission, queued bytes are exactly the next prefix to write, with at most
   76 alphabet bytes plus an optional leading CRLF. Scratch identity and packet capacity
   remain stable. A write failure retains only already committed effects.
4. pendingCRLF is consumed only before a complete group, never before the padded tail.
5. Each normal read/write uses the original stream objects and overloads. Error exits
   preserve exception identity and leave ownership with the caller.

The active pair uses the permitted semantic-action abstraction of iteration. Its
`FOLD_BASE64_WINDOWS` action takes input/output streams, the line flag, window size and
groups-per-line. The solver matches the action/arguments and infers 98304 and 19 from the
source specification. The target JavaAccessor binding uses JDK encoding value primitives
and explicitly implements this effect protocol. Generated code has no dependency on
MiGBase64 or the test model.

This is a trusted implementation boundary: declaring the same semantic action does not
prove the internal loop by induction. Source/action fidelity and target/binding fidelity
are supported by original/generated trace tests and fuzzing. The existing finite-trace
SMT proof is relative to that semantic contract. A stronger internal proof would require
loop-state and exception-effect reasoning; it is not claimed by this implementation.

## Acceptance matrix and coverage accounting

Deterministic checks cover all residues mod 3, 57/58/59/60 and 114/115/116/117-byte line
boundaries; one/two-window boundaries; and the 19-window counter alignment. Whole-input
value checks are independent of the model's packet scheduling. Trace checks cover short
bulk reads, default InputStream bulk behavior, bounded zero returns, EOF, null streams,
injected read/write failures, partial progress, zero-length writes, default OutputStream
bulk dispatch, exception identity, and absence of flush/close.

Fuzz input sizes and chunk sizes are bounded before invoking either side. Large cases use
coarser read chunks and direct bulk-write fixtures to bound trace size; default bulk and
single-byte dispatch are tested on small cases. This is a test-generation bound, not a
restriction added to the source contract. Fuzzer findings retain replayable inputs.

Model targets use `verification_kind=spec-conformance`; generated-code targets use
`verification_kind=migrated`. Both fail on the first mismatch.
Base64IO has 48 executable lines: 46 in encode, one in static initialization, one in its
public constructor. Report the construction check separately and retain both complete
MiGBase64 classes in every denominator. The model comparison is separate from the active
encode migration; the public constructor is not included in the migrated API subset.

## LibSL migration validation

The source call in `source-base64io/src/main/java/Api.java` passes through the normal
Migrator → TraceSolver → ParamSolver → Generator pipeline. `generated-base64io` contains
the resulting Java; the original import is removed. JDK-only compilation is asserted with
an empty classpath, and generated code calls neither Base64IOModel nor Base64IO.

The target binding is an expression returning an anonymous JDK-only implementation.
The existing JavaAccessor mechanism emits it inline; there is no library-specific branch
in the generator. Generic annotation strings are now decoded once, allowing escaped
newlines/quotes. Encoding values come from java.util.Base64; packet scheduling, failures,
empty writes, padding and pending CRLF follow the semantic loop contract above. Stable
JVM default charset makes the private per-instance alphabet observationally equivalent
to the source's private static table under this contract (allocation counts are excluded).

The migrated API is `encode(InputStream,OutputStream,boolean)`. The source constructor
is tested only as a separate model/API smoke check, not presented as migrated code.
The two new Base64IOFuzzTest targets share input generation with the model targets, but
reflectively invoke the actually generated class. They compare exact output and I/O
traces, reused buffers, exception class/identity, partial effects and ownership. Every
successful run is additionally checked with the independent whole-input value oracle.
The 19-window case and default bulk-method behavior have deterministic migration tests.
UTF-8, windows-1252 and UTF-16 are also checked against generated code in fresh JVMs.

SMT result: action correspondence with stream/flag arguments and constants 98304/19.
It is not a formal proof of the handwritten JDK binding internals. Validation: build and all **121 JUnit tests passed**, including four migration tests
and fresh-JVM generated-code checks for all three charsets. Two strict migrated-code
fuzz targets ran with 10-second budgets: **48,982 original/generated encoding comparisons,
zero differences**. The source library's encode method has **46/46 executable lines and
20/20 branches** reached by these targets. Together with static initialization this is
47/48 Base64IO lines; the remaining line is the source constructor, deliberately not
included as a migrated operation.

The migrated-only complete MiGBase64 jar now has **283/284 lines (99.65%)** and
**228/228 branches (100%)**, with both classes in the denominator. The combined 30-target
report remains 284/284 lines and 228/228 branches because the separate public-constructor
conformance test covers that final line. Coverage of hexutils is unchanged. All reports
retain original-bytecode snapshots and SHA-256 input manifests. Existing saved compatible
probe datasets were reused; this is not described as a fresh full 30-target experiment.
